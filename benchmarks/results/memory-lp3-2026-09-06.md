# Ink memory investigation on LP3

Measured 6 September 2026 on the physical Light Phone III (TLP301), Android 14. **Keep QuickJS-ng for now. First reduce eager web-platform initialisation, allocation churn and mounted row counts.** These experiments reduced counter PSS by about 4.8 MiB and scrolling PSS by about 14.3 MiB in combination. They do not yet make Ink the lowest-memory framework.

The production source and original benchmark fixtures were restored after the initial investigation. Experimental changes are saved as patches alongside raw measurements. README figures remain unchanged. Existing unrelated documentation edits were preserved.

Follow-up: lazy web globals and one-off startup GC/Android allocator purging are now applied to production source. The lazy loader preserves globals replaced by application code; collection waits for pending jobs to drain and runs once after the one-second startup deadline. TypeScript checking, `cargo check -p ink-runtime`, runtime formatting, the Android release build and first-access web API smoke checks passed. The LP3 counter mounted and incremented; one idle sample was 29,613 KiB PSS (28.92 MiB), a smoke measurement rather than a replacement benchmark. The repository-wide formatting check reports existing differences outside these changes. No tests were added. The Porffor spike was removed from the repository, and QuickJS remains the runtime.

## What the README measures

The current README compares release ARM64 counter and 1,000-row scrolling apps on LP3: APK size, Android activity launch timings, idle whole-process PSS, CPU time for injected interactions, warm-cache clean build time and continuous-scroll frame intervals. It does not measure the JavaScript heap separately, peak allocations, battery use or complete GPU memory. All 1,000 rows are mounted; the fixtures are not pixel-identical.

Published idle PSS is Ink 35.5 / 45.6 MiB, Expo 54.7 / 101.6 MiB and Light SDK 18.3 / 32.5 MiB, counter / scroll. Thus the published counter gap to Light SDK is 17.2 MiB. The earlier 82-byte JavaScript engine experiment is not representative of the present React/polyfill workload. [README](../../README.md), [current Ink methodology](ink-react-lp3-2026-09-06.md), [comparison methodology](expo-light-sdk-lp3-2026-09-06.md).

## 1. Stop paying the web-platform cost in every app

`packages/ink/src/index.ts` unconditionally imports `./web`. That eagerly installs URL, streams, fetch, WebSocket, Blob and related classes, whether the app uses them or not. `whatwg-url` brings `tr46` 5.1.1: its mapping table contains 9,185 entries and **11,104 nested arrays**. [Entry point](../../packages/ink/src/index.ts), [web globals](../../packages/ink/src/web.ts), [dependency lockfile](../../bun.lock).

QuickJS instrumentation confirms the cost is live allocation, not just APK bytes:

| Counter QuickJS metric | Eager web | Lazy web |
| --- | ---: | ---: |
| Arrays after startup GC | 11,129 | 23 |
| Accounted used bytes after GC | 3,279,298 | 2,128,937 |
| Allocator-accounted bytes after GC | 3,804,719 | 2,360,568 |

These are engine counters, not PSS. Native heap PSS also includes Rust, allocator overhead and native dependencies. Removing all web code reduced the counter bundle from 490,372 to 135,568 bytes and whole-process PSS by 9.59 MiB. That is evidence of an avoidable subsystem cost, **not a promise that a compatibility-preserving fix will recover all 9.59 MiB**.

The simple lazy experiment recovered only 2.08 MiB of counter PSS; combined with GC/purge it recovered 4.85 MiB. The lazy functions still compile and retain code from the large bundle. Instrumentation shows roughly 1.01 MB of JS function storage after GC for the lazy version versus 0.69 MB for eager initialisation, so a getter wrapper alone is not the whole solution.

Recommended implementation:

1. Split web support into independently initialised groups; preserve the public globals and first-use behaviour. Avoid initialising URL/IDNA just because an app needs a stream.
2. For a larger saving, package optional runtime modules separately and load/evaluate them on demand. This requires compiler/runtime work because current builds emit one source bundle. Alternatively investigate compact IDNA data representation or a compatible native URL implementation. Preserve internationalised-domain behaviour; simply dropping the table is not acceptable.
3. Offer explicit minimal-runtime packaging only if API availability is documented. Source scanning cannot reliably infer all global accesses through dependencies and reflection.
4. Consider pinned QuickJS bytecode for release modules to reduce parsing and startup allocation pressure. Measure retained heap as well as startup; bytecode is not a demonstrated steady-state saving here.

The saved lazy patch is intentionally a feasibility prototype. Its global setter/initialiser interactions, descriptor behaviour, re-entrancy and partial failure semantics need designing before production. All web APIs used at runtime will still need their memory eventually.

## 2. Reduce temporary native allocations, then reclaim at sensible boundaries

The baseline counter's native heap PSS was about 16.6–16.8 MiB, while the unvirtualised scroll was about 27.4–28.1 MiB. QuickJS's after-GC allocator accounting was only about 3.63 MiB / 5.01 MiB. These quantities have different accounting and must not be subtracted to produce an exact Rust allocation total. Nevertheless, replacing the JS interpreter alone cannot be assumed to remove the native heap.

A one-off GC freed roughly 0.20 MiB of QuickJS accounted used memory in the counter and 1.52 MiB in the scroll fixture. PSS fell much less than these allocation counts might suggest. Following GC with Android `mallopt(M_PURGE, 0)` improved PSS further. The Android allocator documents this operation as returning unused memory to the kernel. [Bionic allocator API](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/include/malloc.h), [raw engine counters](memory-lp3-2026-09-06/quickjs-all.txt).

The prototype performs this once approximately one second after runtime startup. A production policy should be lifecycle/idle aware, run GC on the JS thread, rate-limit expensive work and measure purge duration. Repeated purging can trade memory for page faults and CPU on the next interaction. Do not force collection or purging on every frame/commit merely to improve an idle number.

Concrete allocation work to profile next:

- Decode native commit messages directly into typed operations, avoiding the generic `serde_json::Value` tree followed by another operation conversion.
- Replace retained string-keyed JSON props with compact typed properties where practical.
- Reduce repeated property conversions, temporary commit payloads and full native subtree reconstruction on structural updates.
- Measure allocation counts and high-water capacities before adding blanket shrinking; capacity reuse also saves CPU.

The current ownership path includes React fibres and host instances in JS, `ReactTree::HostNode` JSON props, the engine's native `Node` tree, `Scene`, and renderer-prepared data. This duplication is a structural target, especially with many mounted rows, but the saving from a particular redesign has not been isolated. [JS renderer](../../packages/ink/src/renderer.ts), [React native tree](../../crates/ink-core/src/react.rs), [engine](../../crates/ink-core/src/lib.rs), [renderer](../../crates/ink-renderer-wgpu/src/compact.rs).

## 3. Use virtualisation in applications; retain the honest benchmark

Existing `List` with `itemHeight={40}`, `gap={24}` and stable item keys reduced this list's PSS by **9.51 MiB** without changing the runtime. It mounts a viewport window rather than every row. Keep the current unvirtualised benchmark for comparison and add a separately labelled virtualised workload. Durable row state belongs outside mounted row components. [List implementation](../../packages/ink/src/list.ts), [List contract](../../docs/lists.md), [experimental fixture patch](memory-lp3-2026-09-06/virtualised.patch).

## 4. Attribute the remaining baseline before changing renderer or engine

The LP3 denied `/proc/<pid>/smaps_rollup` access for the release app. `dumpsys meminfo` reported Graphics PSS as zero despite Vulkan rendering, so this run does not establish total GPU consumption. PSS apportions shared pages and is distinct from allocator counters and virtual reservations. [Android memory accounting](https://developer.android.com/tools/dumpsys#meminfo).

Next build a dedicated profileable release flavour and collect native allocation stacks, tagged QuickJS phase counters and GPU allocation/buffer data. Separate runtime boot, bundle evaluation, first commit, Vulkan startup, idle, scrolling, navigation and background/resume. Re-run interleaved comparison fixtures after improvements, including peaks and sustained interaction, before claiming the lowest footprint.

The wgpu hint experiment showed no useful PSS saving. It changes allocator strategy, not a guaranteed resident-memory cap. Ink already requests frame latency 1, starts with small instance buffers, and allocates a 1024² R8 glyph atlas (1 MiB nominal texel payload). Its 8 MiB image cache value is a budget, not an eager allocation. Surface detachment already drops the renderer; do not assume all GPU resources survive backgrounding. [wgpu hint documentation](https://docs.rs/wgpu/30.0.1/wgpu/enum.MemoryHints.html), [renderer allocation code](../../crates/ink-renderer-wgpu/src/compact.rs), [Android surface ownership](../../platform/android/native/src/android.rs).

If remaining allocation stacks point to Vulkan/driver fixed costs, compare a minimal alternative rendering backend with the same scene and workload. That is a larger investigation, not a justified rewrite today. Likewise, reducing QuickJS's 64 MiB allocation limit or the JS thread's reserved stack size does not automatically reclaim equivalent PSS; the observed stack PSS was only about 0.64 MiB for all threads.

## Evidence and reproduction

Base revision `29e729c5fc0364ef14a981829a814bb27c49a660`, with pre-existing changes in `docs/implementation-plan.md` and `docs/verification-2026-09-06.md`. All measured APKs used the release ARM64 build and existing benchmark signing configuration. Android thermal status was 0 when checked during and at the end of the investigation; no animation, keep-awake or other persistent device settings were changed. The device was woken and benchmark activities foregrounded.

[Raw measurements, patches and screenshots](memory-lp3-2026-09-06/), [sample summary](memory-lp3-2026-09-06/summary.json), [APK hashes](memory-lp3-2026-09-06/apk-sha256.txt), [profiling script](memory-lp3-2026-09-06/profile.ts). APK copies remain temporarily under `/tmp/ink-memory-apks`; hashes identify the measured binaries, not a guarantee those temporary files persist. The script records launch/meminfo only; it does not install APKs, exercise interactions or restore device state. Its device serial and output directory are local to this investigation.

To reproduce, use an isolated checkout of the base source, apply the relevant patch(es), build both apps using the README's release signing workflow, install the resulting APKs, and run the script with a new variant label/output directory. `gc.patch` and `gc-purge.patch` are alternatives. Combined uses `lazy-web.patch`, `gc-purge.patch` and `virtualised.patch`; the no-web experiment uses only `no-web.patch`. Uninstall temporary apps afterwards. Do not apply these diagnostic patches as production fixes.
