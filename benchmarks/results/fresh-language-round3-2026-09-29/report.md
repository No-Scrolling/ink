# Fresh language ownership audit, 29 September 2026

## Conclusion and evidence status

Ink should continue to move stable, deterministic framework work into Rust, while keeping arbitrary application execution, React component lifetimes and observable JavaScript semantics in QuickJS. The useful boundary is a validated native description or retained data handle, not the TypeScript file extension. There is substantial work already in Rust; several remaining improvements remove repeated work *inside Rust* or between Rust and Android rather than translating more JavaScript.

The strongest immediate directions are:

1. Preserve the verified Proxy and function-property controls before expanding automatic native compilation.
2. Extend retained native collections and typed expressions to avoid full JavaScript projections, while keeping executable rows on React.
3. Remove repeated JSON envelope processing and duplicated native collection/version storage.
4. Make recoverable collection replacement stage only affected state, preserving its current atomicity.
5. Measure and improve native incremental layout/render preparation; those costs remain after reconciliation disappears.
6. Move the deterministic playback DSP loops still written in Kotlin into a portable Rust processor only if block-level JNI measurements justify it.

This is an independent source reconstruction. No earlier generated audit, fix or benchmark report was read. Only newly created evidence under this directory was inspected. Application source and repository tests were not edited; no tests were added. Existing checks were run. No device was reserved, installed, reset or changed. No visual defect is claimed.

Initial observed HEAD: `4ca730d4085ee15ddde667963869a1109db2b67d`. The working tree contains extensive tracked modifications and relevant untracked code, so HEAD alone is not the reviewed source. `provenance.json` hashes 1,146 tracked and non-ignored untracked inputs outside previous report/output directories. Individual headless runs also record their exact input, dependency and artefact hashes. Source changes during the review were explicitly announced; historical and final evidence are distinguished below. No parent report or another reviewer's findings were used as audit input.

Labels in this report:

- **Demonstrated**: observed in a fresh diagnostic or existing real-runtime fixture.
- **Source-established**: control flow/data structures establish the operation or allocation, without a claimed timing improvement.
- **Opportunity**: a proposed improvement requiring measurement and semantic acceptance.
- **Restriction**: a documented limitation; it is not presented as an unconditional defect.

## End-to-end reconstruction and costs

### Startup

The Rust compiler writes generated entry/routes/build modules and invokes Bun. The build script identifies package native requirements, resolves imports/assets, analyses native-list row eligibility, invokes Oxc for React/app transformation and constructs a production bundle. Imported assets receive content hashes. Rust prepares icon masks and the compatibility manifest. These are developer-machine stages.

On Android, `MainActivity.startJavaScript` reads `app.js` into a Kotlin String, passes it through JNI, obtains a Rust String and starts `ink-js`. `AppRuntime` creates a full QuickJS context, installs Rust functions plus the host/encoding/event JS shims, evaluates source, reports ready and drains jobs. React then mounts the application; commits cross the native queue; Rust expands optional host descriptions and builds/layouts the scene; Kotlin schedules a drawable frame and Vulkan prepares/presents it.

The web compatibility runtime is already lazily installed: exported globals trigger the synchronous web loader; split-web builds defer loading `ink-web.js`. The loading path still reads Kotlin source, copies through JNI and evaluates it in QuickJS. Do not charge unused URL/stream/fetch initialisation to every application, or recommend adding a laziness mechanism that already exists.

Runtime guards currently include a 64 MiB QuickJS heap limit, 512 KiB engine stack, a 2 MiB JS-thread native stack, 256-entry command/event channels, 1 MiB individual envelope limit, a shared 16 MiB queued-payload budget and a separate 8 MiB outgoing binary budget. One startup GC occurs after roughly one second once jobs settle. These are boundaries, not a total-process-memory bound.

Opportunity: packaged QuickJS bytecode or source-free native description assets can avoid some on-device parsing/copies. Bytecode must have the exact dependency/build/options fingerprint, support development fallback/source maps and never accept incompatible bytecode. Source loading should take bytes/file descriptors where possible rather than require UTF-8 → UTF-16 → UTF-8 copies. Measure cold process-to-first-scene and first presented frame, lazy-web first-use latency, heap/PSS and retained bundle bytes separately. Current mount/setup observations (17.346 ms ordinary; 27.536 ms bindings) are harness startup, not Android launch measurements.

### Pointer/input to ordinary React scene

Pointer-up reaches native hit testing and a native action. Ink routes row actions where necessary, sends the event through the incoming runtime queue, parses the envelope in `native.ts`, selects the current JS handler and temporarily applies discrete event priority. Application code updates state. React executes/reconciles, and the custom renderer accumulates creates/updates/text/inserts/removes/hide operations. A microtask flushes passive/synchronous work and pending native-view values before `__inkCommit`.

`commit.rs` walks the JS operation array and owns Rust protocol operations before queueing them. Text batches take strings directly through QuickJS's owned C-string encoding and compact `SmolStr`; no text JSON document is required. **Create/update props and values/collections still use QuickJS JSON stringify followed by serde JSON deserialisation.** A zero `decode` result in the harness means no later whole-commit JSON decode; it does not mean zero JSON conversion.

For the selected 500-cell fixture, a refresh changes 500 cell labels and one summary, plus 50 row gaps. Source-derived expected protocol structure is one text operation containing 501 ID/string pairs and 50 row-property updates, where text batching remains intact. Thus roughly 50 property stringify/parse calls remain; 501 text values are encoded/copied into native ownership. This count excludes fixture setup and verification and should be instrumented if exact per-update counts become an acceptance condition.

Rust applies the host changes, finds update targets, removes descendants already covered by changed ancestors, builds replacement nodes and tries incremental replacement. Fixed-width/tabular text can patch scene text without relayout; spacing or structural changes relayout the native scene. Kotlin drains in bounded main-thread slices and schedules/merges frames around GPU readiness and touch/fling work. Taking React out of the update path leaves layout and renderer preparation intact.

### Native-view updates

`nativeView` builds one ViewScope per React mount. The JS scope keeps callbacks/values and the serialised definition, not a mutable JS host-instance tree. React retains mounting/Activity lifetime. Layout-effect attachment registers actions and starts subscriptions; detachment cancels pending work, runs all clean-ups in reverse order and reports aggregate failures. Values changed while detached remain dirty and are scheduled on reattachment.

JS `derive` remains application calculation and scans its declared derivations when dirty work is flushed. `compute(expression)` describes a separate finite-number/JSON native language. Rust builds a dependency index once, evaluates dependants topologically, collects changed target properties and emits ordinary native operations.

The binding fixture declares 2,054 derived expressions: 1,500 per-cell ID/prefix/label sources, 50 row-visibility sources, 500 cell-visibility sources, gap, summary and two toggle labels. A normal tick affects 500 final labels, the summary and gap; static prefixes/visibility are not recalculated merely because they exist. Nonetheless expression evaluation uses serde JSON values, clones selected operands and constructs intermediate values. `expand_views` gathers patches, snapshots non-text host properties and synthesises ordinary Update/Text operations. The roughly 0.237 ms measured apply/layout includes that native computation, rather than proving it vanished.

A useful next Rust interface is a prevalidated typed program with source/target handles, typed finite f64/string/bool slots, topological dependants and a dirty target list. Common formatting can write directly to retained output storage; geometry updates should validate only changed fields. Generic JSON descriptions can remain the author-facing serialisation/fallback. Compile once at mount; do not parse instructions or reconstruct full property maps on every tick.

### Lists, collection mutations and callbacks

The compiler's supported fixed JSX shapes avoid React row creation/reconciliation. It retains the original callback for fallback and constructs a JS projector, native template, key identity and captured-value provider. Calls in displayed values, custom components/hooks, refs/spreads and conditional shapes retain React. Standard Row/Avatar/message/player host composites also construct their presentation children in Rust.

The compatibility `ReactList` maintains all keys and content versions, checks uniqueness, estimates a native window, renders only the current range (32 rows initially), reacts to native window notifications and manages pagination callbacks/errors. On new data it maps all keys, builds a new record Map/version array and JSON-encodes/UTF-8-encodes metadata to enforce the 128 KiB limit. Native height/windowing remains shared with compiled rows.

`CompiledList` validates plain item data and capture snapshots. It retains all original items plus row records/projected values in QuickJS. With a new items array, even a one-record edit traverses all N items, creates a Map, an output array and N RowRecord wrappers; changed projection may be only k records if item/index/scope identities permit reuse. Reordering changes indices and can reproject many/all records. Changed captures require projecting every row. The WeakMap patch records avoid a second full deep comparison in the renderer, but do not remove the first scan. An unrelated parent update with stable items/key/template/scope can return previous records; this is a meaningful optimisation already present.

The source reviewed during final validation reuses shared object nodes in capture snapshots and comparison. This matters independently of Rust: a depth-d DAG with two references to the next node has only d+1 objects but 2^d paths. Snapshot/comparison must scale with unique objects and edges, rather than unfold every path. Plain-data eligibility currently uses a fresh WeakSet per captured top-level value; K aliases to a shared V-object graph can still repeat O(KV) validation even when snapshotting is O(V). Use one fresh validation cache across the capture group, or a single native eligibility/snapshot traversal, while checking observable/cyclic/unsupported values before caching and preserving mutable captured primitive updates. This is source-derived work, not a measured speedup claim.

On row events, `onRowEvent` resolves a current key and re-executes the **entire projector** to recover the callback path. It therefore recreates unrelated projected text/nested objects/closures for a click. This is intentional freshness handling but a removal opportunity: separately compile per-action selectors/closure constructors and carry logical key/index/current capture metadata. Do not retain a stale application closure or cache callbacks solely on visually equivalent native data. `ReorderList` invokes its arbitrary `getLabel` during its internal projector; message projection also performs link/time formatting. Avoid re-running those just to invoke an action.

Rust `NativeList` owns item maps, keys, indices, version arrays, mounted rows and native event mapping. It initially materialises at least 32 rows then can make up to eight window-refinement passes. The window is bounded by visible/overscan rows, not total records. Every materialisation pass currently reinserts every retained wanted row. Host insertion removes the previous child by a linear scan/retain and appends it again; W row reinserts can perform O(W²) child work despite O(log N) Fenwick height lookup. Bounded W makes this smaller than O(N) reconciliation, but removing redundant inserts is still useful.

Sparse item updates preserve key storage and patch height metrics for only changed rows. However `Arc::make_mut(list.versions)` must copy the N-element u64 array while the current engine root also retains it through `render_native_list`. This is source-established O(N) version-copy work: 8,000 bytes at N=1,000, 800,000 bytes at N=100,000 for a single edit, excluding allocation overhead. Height metrics retain their own Vec versions/keys. A handle to version storage, chunked copy-on-write storage or sparse revision map should replace this shared mutable full-array boundary.

`ViewCollection` is a stronger ownership boundary: JS sends reset/insert/update/remove/move/reverse commands with monotonically reserved revisions, while Rust retains records. Single-row field updates produce record deltas. Order operations use Vec keys: locating anchors, removing/moving and insertion are linear; a reverse is linear; repeated insert/move batches can become O(kN). Retained JSON records are Arc-backed, but the collection and NativeList still maintain separate maps and separately cloned records on mount/patch. `Collection.data()` and whole-collection binding selection materialise/clones all N records. `expression.length(collection)` already avoids that materialisation. NativeList bound items take the specialised delta path on updates, which is an existing optimisation to preserve.

Native collections should expose one shared immutable record-store/order handle to list consumers, with direct keyed lookup and mutation events. This removes a Rust-to-Rust projection/encoding boundary; merely moving the JS projector to Rust while still recreating a full array would miss the main opportunity.

### SQL and persistent store

Ordinary database query: JS validates parameter types and sends a generic call; Kotlin opens the asset database and runs a read-only cursor on a single executor; rows become JSONObject/JSONArray; each row is independently stringified and UTF-8-encoded to count its bytes; the full array is stringified; the result is encoded inside a generic envelope; QuickJS parses that envelope and the package parses the row-array string. Row limits are 10,000 and approximately 400,000 row JSON bytes; unsupported blobs and unsafe integer results are rejected. Read cancellation uses Android CancellationSignal.

`queryInto(collection, ...)` avoids constructing query rows in QuickJS. Kotlin still constructs JSON rows/string, copies them through JNI and Rust deserialises them. It reserves the destination revision before dispatch; Rust ignores results older than edits/results already applied. That prevents late overwrite and is part of the API contract, not an accidental missing update.

Recoverable destination application clones **the entire ReactTree and Engine** before replacing the collection and refreshing windows. Engine staging copies the current root, scene, list metrics/height indices, inputs, pointers, requests, caches and related structures, while preserving live animation/decoder ownership on commit. The copying is deliberate rollback protection. Replace it with a transaction-scoped staging plan for the affected collection, expressions, lists and resulting scene, with a single validated commit. Do not delete atomic staging as a performance shortcut.

`createStore` deliberately retains user decode/migrate/transform functions in JS. Kotlin SQLite supplies actual transactional revision compare-and-swap. An update can require a read/write pair repeated up to 16 times; the transform may run more than once under contention. Migrating an arbitrary transform to Rust would change both execution semantics and application authoring. Rust can own opaque JSON/version bookkeeping and notifications or add an explicitly typed patch API, while existing application transforms continue to run in JS with CAS retry semantics.

The final store adapter validates the **escaped result envelope**, rather than only raw stored text, before persisting a value. It reserves the widest safe revision and request ID so subsequent increments cannot make the stored value undeliverable. Generic native result delivery also measures its complete UTF-8 envelope, disposes resource-bearing results on overflow and returns a small protocol error. These bounds protect correctness but perform serialisation and byte-array allocation; a typed bridge should retain equivalent bounds without recreating large strings merely to discover their size. No Android SQLite boundary/cancellation experiment was performed by this reviewer.

### Binary, fetch, uploads and files

The native binary channel already avoids base64/JSON bytes for network and managed-file operations. Outgoing JS bytes are borrowed only while no JS executes and copied into an owned Vec before asynchronous queueing; this preserves subarray boundaries and prevents later JS mutation affecting native work. Incoming Vec ownership can be transferred to a QuickJS typed-array backing allocation. JNI still constructs/copies byte arrays in both directions. Do not describe the path as universally zero-copy.

Generic call path source-derived conversions: JS stringify of an envelope; Rust message parsing; Rust joins queued calls into a JSON array; JNI String copy; Kotlin JSONArray parse; Kotlin payload `toString`; adapter JSONObject parse. `__inkPostBytes` additionally parses the binary call to validate/associate its ID. Results can carry an already JSON-formatted value as an escaped String inside another JSON envelope, requiring a native-envelope parse and a package-specific parse. This boundary is repeated for each stream chunk/native call.

JS stream semantics remain necessary for application readers, tee/clone, backpressure, disturbed/locked bodies and AbortSignal. HTTP pulls request native 32 KiB chunks with highWaterMark 0. Ordinary upload first creates a native temporary file, then sequentially awaits one binary write request per 32 KiB chunk before starting the network request. A 1 MiB body is 32 writes plus upload-open and stream-open; later response reads and close add more requests. This is request/body preparation work, not streaming upload as the application produces data. Large requests also add file append/reopen and disk copy cost. Managed Blob multipart/file segments already bypass bringing file bytes through JS, but still spool a native upload file; preserve this benefit.

Buffered `Body.bytes()` retains every received chunk and then allocates/copies a contiguous body, with a 16 MiB limit. `text` adds UTF-8 decoding; `json` adds parsing and resulting object retention; `blob` copies bytes into Blob storage for ordinary responses. Those copies often implement required immutable/independent-object semantics. Native file-backed Blob optimisations can avoid some copies, but native handles need independent lifetime/disposal and clone/tee semantics. They must not expose mutable temporary files as immutable Blob snapshots without an explicit lifetime/snapshot policy.

NFC still uses `Array.from(bytes)` JSON arrays and hexadecimal response encoding. It is a straightforward candidate for the existing binary channel; APDUs are small, so benchmark call/latency reduction rather than assume it dominates memory or CPU.

File picking/import/share/save, MediaStore permission and managed-file identity are platform ownership. MediaPicker groups all accumulated records into rows, rebuilds ID sets on page appends, and projects all grouped rows on selection changes. Native keyed data/selection handles could reduce repeated JS work, while app `onSelect` and platform importing stay unchanged. Image preparation uses BitmapFactory orientation/scaling/JPEG operations; renderer image decode already uses native AImageDecoder and Vulkan caches. Replacing codecs/platform operations needs codec/orientation/colour/animation parity, not just a language preference.

### Audio, rendering and ancillary modules

Pitch/level capture does not require a JS round trip for every numerical sample. Kotlin AudioRecord reads 4,096 mono samples at 48 kHz, copies read arrays, coalesces latest input and posts to the UI thread; JNI copies those samples into Rust; Rust coalesces/works on a DSP worker and publishes latest readings. Generations prevent stale outputs after disable/reconfigure. Native capture readouts and playback clocks can update directly, while hooks optionally receive meaningful controller state.

The pitch calculation is already Rust and algorithmically expensive: for non-silent 4,096-sample input at 48 kHz, maximum lag is 960 and the direct squared-difference loop visits sum(4096-lag), lag 1..960 = **3,471,360 sample pairs** per block. Approximately 11.719 blocks/second gives roughly **40.7 million pairs/second per enabled pitch processor**, before normalisation/search/formatting. Silence returns early. Reusing Vec capacity is already present. Downsampling/FFT/autocorrelation or shared analyses across processors may beat language translation, but require controlled accuracy, octave/noise/reference/latency acceptance. The worker clones controller configuration maps/strings on each sample wake even without configuration changes; immutable config snapshots and typed reading structures can remove those allocations.

QuietAudioProcessor and VoiceAudioProcessor are still Kotlin deterministic loops over PCM. Quiet detection/crossfades, biquads, energy accumulation, gain/compression and look-ahead peak limiting are suitable Rust algorithms. Media3 buffer negotiation/flush/EOS, session/focus/foreground playback, queue persistence and platform decoding stay Kotlin/Android. Use a persistent native state handle with configure/process-direct-buffer/flush/drain/reset, one JNI call per PCM block, no per-sample JNI calls and no callback/mutex/allocation on the real-time path. Measure block CPU, allocations, peak latency, audio underruns, startup and output equivalence first. This is an opportunity, not evidence of current audio defects or a measured improvement.

Renderer preparation is entirely native already. Scene revisions gate preparation; scroll-only frames can update a small transform/scrollbar without recreating geometry. For changed scenes, renderer code compares retained quads/text/image runs, rebuilds combined instance vectors, identifies a changed upload span and keeps a full CPU instance snapshot. A sparse change can still scan/copy entire instance arrays even when only a narrow span is uploaded. Variable glyph counts can move later ranges. Dirty run ranges/retained instances and incremental layout dependencies could remove native work; no TypeScript-to-Rust translation is involved. Preserve clipping/order/UV/cache/lifetime correctness. Any later visual claim/change must use agent-tools saved pixel comparisons and OCR, not a preview alone.

Android system glyph rasterisation uses Paint/Typeface/Canvas and owns fallback Japanese/emoji platform semantics. The Vulkan atlas and native geometry already own caching. Replacing the Android fallback with a bundled native font engine is a separate compatibility project involving shaping, grapheme clusters, fallback fonts and OS appearance, not a low-risk deterministic-loop move.

Maps validates and projects all markers on each React render, then compares against the previous update; a keyed native marker handle/patch protocol can reduce this work. Keep camera/marker callbacks and map SDK lifecycle in JS/Kotlin respectively. Video, camera, notifications, Light SDK, auth, location and secure-store are mostly thin adapters; moving their small validators to Rust often adds a binding call while retaining the necessary JS/Android work. Background user tasks still execute in isolated QuickJS contexts; WorkManager constraints/state persistence are Android ownership.

The untracked wallet package introduces deterministic JSON schema/field grouping and Kotlin pass archive/metadata/artwork handling. It is mostly user-visible formatting and platform file work, not a demonstrated hot loop. Portable archive validation/content-addressed metadata can be a Rust module later, but localisation/date/timezone and Android share/launch/file lifetime must remain equivalent. Do not silently remove Valibot/application decode semantics to avoid a second validation pass.

The historical `projection-diagnostic.ts` ran the actual renderer/list implementations in Bun at the initial source snapshot, with a transparent Proxy for each of 1,000 plain-looking records. It records accesses to `label`, without changing the application's tree/native source. Bun does not install Ink's QuickJS-native Proxy helper; this result must not be described as the final QuickJS behaviour.

| Control/path | Proxy label reads at mount | NativeList created | Runtime report |
| --- | ---: | ---: | --- |
| ReactList | 32 | No | No error |
| Compiler-attached native row plan | 1,000 | Yes | No error |

The separately saved compiler transformation accepts the corresponding inline `item.label` JSX row. The diagnostic uses the same template/projector shape through the internal compiler interface; it does not replace React with fake hooks or a mock list. Output: `projection-diagnostic.json`, transformation: `compiler-proxy-case.txt`.

Without a native identity check, a transparent Proxy can return an ordinary prototype/data descriptors while running arbitrary `get` traps later. Reflection itself can also invoke proxy traps. Off-window projection in the historical control therefore executed observable application behaviour that the compatibility path did not execute then. The fixture does not claim a Rust/GPU visual difference or measure Proxy cost on QuickJS.

**Historical restriction/falsification:** the initial native-bindings documentation told Proxy/observable-coercion users to use a block-bodied renderItem, and native lists require immutable plain records. The historical observation was a shortfall against the full-JS-semantics objective with a documented opt-out, rather than a claim that the initial documentation promised to recognise Proxies. Mutating an item in place is excluded by the immutable-data contract and is not reported as an independent defect. The final documentation explicitly describes Proxy fallback.

The final implementation uses the installed `__inkIsProxy` native helper, backed by pinned QuickJS-ng `JS_IsProxy(JSValueConst)`. Objects become cacheable only after native non-Proxy eligibility is established; Proxy detection precedes reflection on new objects and includes callable Proxies. A cached ordinary object cannot subsequently acquire Proxy identity. This resolves the demonstrated Proxy path in the actual runtime.

`proxy-final-quickjs.ts` bundles the actual renderer and is executed by `AppRuntime` in the small observational Rust driver saved in this directory. The driver consumes real runtime events and terminates after the tagged result; it does not replace React hooks or edit the runtime. Native commits are observed before passing them to the real native commit encoder. It does not apply them to a scene, so this is a JavaScript-observability control, not layout/pixel verification.

### Established defect, corrected during final validation: callable objects with properties

Function objects may carry application data and accessors. The version examined before the final fix checked callable Proxy identity but then returned true for an ordinary function without examining its property descriptors. `captureValue` likewise captured function identity without fields. The compiler accepts ordinary property access on a captured function: `renderItem={item => <Text>{config.label}</Text>}`.

`function-property-runtime-builder.ts` saves the original JSX and its **actual compiler transformation**, then bundles the real public List/renderer. The release AppRuntime driver observes commits and getter counts for 1,000 immutable plain items. `config` is either an ordinary function with a `label` getter, or an ordinary function with a writable `label` data property. The block-bodied React control uses the same config and items. No custom runtime hooks, mock React implementation or Proxy are involved.

| Release control | React public List | Compiler-transformed public List |
| --- | --- | --- |
| Function `label` getter, initial mount | 32 getter reads | 1,000 getter reads and a NativeList |
| Same getter, unrelated parent state update | 32 more getter reads | 0 more reads |
| Function data property `label`: Before → After, parent update | One text operation containing 32 visible `After` labels | No update operation; native records retain Before |

Historical evidence is `function-property-initial-quickjs.json`, plus `function-property-initial-source.tsx`, `function-property-initial-runtime.tsx` and `function-property-initial-bundle.js`. Both paths reported no runtime error. This is a semantic/commit defect, not a screenshot-based visual claim: no scene/GPU image was inspected, and no rendered-pixel defect is asserted.

**Boundary:** immutable item records were respected; the changed value is a captured function property. Arbitrary observable coercion still has a documented block-bodied opt-out, but this case is plain field access and the documentation says accessors retain React rendering. No automatic migration should rely on a blanket “functions are harmless” eligibility rule.

The final fix validates/snapshots function own fields as well as ordinary-object fields, rejects accessors/observable coercion hooks, and recognises only the bare intrinsic function prototype (Object.prototype parent and sole own data constructor back-reference). That intrinsic prototype remains an identity leaf in snapshots. This avoids a false cycle rejection for ordinary declared event handlers; customised prototype graphs retain ordinary validation/cycle fallback. Function Proxy checks still precede reflection.

The expanded **final release** control has 16 cases and no errors. Own/prototype getters both fall back with exactly 32 reads at mount and 32 on parent update. A direct mutable function data field stays native and emits one update with **exactly 1,000 changed records, all carrying `After`**. Mutable custom prototype data updates through React; custom metadata cycles fall back. Ordinary declared, arrow and bound callback-only captures remain native. All Proxy controls still pass with zero additional reflection traps. The final actual-compiler depth matrices pass all 28 release and all 28 `ink-dev` cases after the final cosmetic variable rename. Evidence: `function-property-final-quickjs.json`, `proxy-final-quickjs.json`, `compiled-capture-depth-final-{release,ink-dev}.json` and their saved source/transformation/bundles. The existing list fixture also passes fresh callback and sparse-transfer controls. This corrects the demonstrated defect in the final reviewed source.

A future compiler distinction between visual capture dependencies and action-only values could avoid validating/snapshotting metadata irrelevant to presentation; it is now a work-removal opportunity rather than a prerequisite to closing the demonstrated function-property defect.

## Semantic and correctness acceptance boundaries

1. **Getters/proxies/coercion:** property access and object-to-primitive operations remain JS executable behaviour. Purity syntax alone is insufficient. Rust cannot replace ordinary JS expressions with serde JSON arithmetic/stringification. Descriptor inspection must not run user getters; proxy inspection needs a native identity check.
2. **Numbers/strings/truthiness:** expression APIs are explicit finite-number/JSON operations. Division/remainder failure, negative zero, NaN/infinity, BigInt, safe integer limits, object identity versus JSON equality, number-to-string exponent/rounding and null/undefined distinctions need defined contracts. UTF-16 string length is already implemented for native expression length/pad; do not substitute UTF-8 bytes or Rust character count. Boolean native conditions must not stand in for arbitrary JS truthiness. Native string concatenation currently uses Rust f64 formatting, which is not JS `String(number)` for all magnitudes; automatic compiler lowering must not reuse it without a JS-compatible conversion.
3. **Callbacks:** function identity is masked to booleans for native event affordance, while JS mounted props/current plans retain actual functions. Native visual equality must not suppress handler freshness. Invoke exactly the correct current logical row/action; do not re-run unrelated executable projection to recover a callback.
4. **Hooks/effects/refs:** React compatibility rows retain normal React semantics. Compiled rows cannot safely erase custom hook/ref/effect lifetimes. Crossing template/fallback shapes currently remounts the list, and docs say so; preserve or explicitly change this behaviour. Activity hide/reveal detaches/reconnects effects while state is retained, including dirty native-view updates.
5. **Inputs:** event-count acknowledgements reject delayed React values older than native keystrokes. Recycled native IDs and free input states must not leak previous text, cursor/focus or callbacks. Keep grapheme/UTF-16/UTF-8 cursor boundaries and Japanese/emoji behaviour; existing headless controls cover some of this, but Android IME is separate.
6. **Atomicity:** SQL query destination replacement is recoverable and staged. Ordinary `ReactTree::apply` is not a general rollback transaction; errors terminate the JS app path. Do not infer all commits are recoverably atomic or rely on live mutation after a failed query. CAS store transforms/retries retain their existing semantics.
7. **Queues/cancellation:** incoming/outgoing queues are bounded by count and payload budgets. Timers/jobs are drained in slices so shutdown/messages are not starved. Binary queue ownership is ID-associated and consumed once. Late adapter results must dispose temporary files/resources after cancellation/session replacement. Existing boundedness is not a total-retained-memory measurement: a received message may move into ScriptRuntime call storage/Kotlin arrays after its queue budget has been released.
8. **Collections:** validate keys/revisions/order anchors and failed edits before recoverable live commit. Native data limits remain 100,000 records; arbitrary JS list metadata has different bounds. Native count/length expressions can avoid materialisation; a whole-array consumer may deliberately require O(N) work.
9. **Platform APIs:** Kotlin owns Android permissions, main-thread View/Surface work, WorkManager, Media3/AudioRecord, HttpEngine/OkHttp, Android Keystore, file content URIs/MediaStore, fallback glyphs and lifecycle. Moving portable computation should shrink these adapters while preserving their thread/callback/ownership contracts.
