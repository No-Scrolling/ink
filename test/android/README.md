Run `bun test/android/run.ts --serial emulator-5554` from the repository root. Android tests are opt-in and require an explicit serial, Bun, `adb`, JDK 17 or 21 (`JAVA_HOME`), Android SDK platform 36 and build tools (`ANDROID_HOME`), and an API 34+ device. Start the prescribed emulator with `emulator -avd Light_Phone_III -writable-system` and wait for boot before running. Gradle may download its pinned build dependencies on first use.

The standalone fixture compiles the real production Kotlin adapters directly and installs `com.vandam.ink.contracttests`. The runner refuses to replace an existing package, takes a per-device lock, and uninstalls its fixture in `finally`. It does not start or stop an emulator or change device settings. Build and instrumentation logs remain in `.test-output/android/`. If a run is forcibly interrupted, explicitly uninstall the fixture and remove its `.test-output/android-<serial>.lock` directory before retrying.

The 33 device contracts cover spline fling timing, audio playback, Handler timeouts and cancellation, late-result ownership, duplicate IDs and completion, pending-request capacity, JSON escaping and the UTF-8 message limit, Android Keystore persistence and authentication, managed-file confinement, managed ranges, local camera response bytes, queued upload cancellation, upload limits and disposal, real HTTP request/response bytes, and idle stream/upload cleanup. Audio checks exercise usage-based external commands, real ExoPlayer audio attributes after item transitions and replacements, session fallback, and per-item usage through Media3 bundles and queue persistence. They also check offload preferences as effects, speed, pitch and routes change; per-track and per-route PCM fallback decisions; and headset single, double and triple presses through a real MediaSession and platform controller. Content-source checks play audio through a real content provider with HTTP caching enabled, round-trip the URI through queue persistence, reject unsupported schemes and verify playback errors for denied access and deleted items. They cannot verify hardware offload or reproduce an offloaded AudioTrack start failure on an emulator. Fling checks compare Android's final distance, fixed duration and cubic reference points, decreasing steps at 60, 90 and 120 Hz, and stop/restart behaviour. The expiry check waits the real 61 seconds; no clock or scheduler is replaced. The controlled queue used for cancellation is the adapter's injected Executor and runs the actual production file operation.

Notification permission checks exercise the production permissions adapter with a controlled LightOS endpoint and real Android permission state. They verify LightOS routing from server 0.2.4, Android routing for older or unreadable versions, and cancellation while reading the version. They also verify that a host denial does not fall back to Android. These checks do not exercise the LightOS Binder protocol or its permission screen.

Push checks call the receiver’s production delivery function with real HTTP inbox responses, Android Keystore credentials and Android notifications. They cover null, empty and unparseable bodies, plaintext fetch-on-wake registration, encrypted delivery and its SHA-256 acknowledgement, and a wake-up without a configured inbox. The encrypted fixture and expected receipt were generated independently with Node crypto. These checks do not exercise UnifiedPush transport or the LightOS gateway.

Tool Manager checks exercise the production shared-file adapter with real files, binary ranges and modification times. They reject traversal and symbolic-link escapes, and check persisted change revisions and cancelled observation. The emulator end-to-end flow covers the system-UID provider and browser transfers.

This fixture exercises adapter and platform contracts without Rust/JNI or application rendering. Rust schedules store and SQLite operations and delivers their results; a Kotlin backend calls Android's built-in SQLite on the Rust workers. Encryption runs in Rust. `test/native/tests/data.rs` covers the shared workers and host embedded backend, and the `android-app` suite covers the system-backed store on a device. It does not claim full end-to-end bridge coverage, cross-process store notification coverage, media/hardware coverage, image preparation coverage, or release network-policy coverage. Its debug HTTP request uses device loopback, which production permits for development; it needs no public network service.
