# Light SDK surface not covered by its docs

Research date: 30 August 2026. This audit compares the official README and `docs/` tree with first-party source at commit [`3df3c24`](https://github.com/lightphone/light-sdk/tree/3df3c24a21247e70ad59e1bc0393ac6d63840bc2). It treats a public client type or function as an API, but does not mistake a permitted manifest entry, server hook, or protocol implementation detail for one.

## Findings

| Surface | What the documentation misses | Relevance to Ink |
|---|---|---|
| Open the LightOS dialler | `LightServiceMethod.OpenDialer` accepts a phone number and the server delegates it to its configured dialler handler. The client README only demonstrates `SetRingtone` and sends readers to the source for the remaining methods; it never names the dialler integration ([documented generic call](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/README.md#L344-L354), [typed method](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/shared/src/main/kotlin/com/thelightphone/sdk/shared/LightServiceMethod.kt#L137-L146), [server handling](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/server/src/main/kotlin/com/thelightphone/sdk/server/LightSdkService.kt#L231-L244)). | Strong candidate for a small `openDialler(number)` action. It preserves LightOS ownership of calling and does not require Ink to expose Android intents. |
| Remote push | The docs show `onPushNotification` in the optional entry point, but the dedicated push section is still `TODO`. Source additionally exposes `enablePushNotifications`, a `StateFlow` carrying the registered endpoint and date, remote-channel registration, endpoint clearing on failure/unregistration, and byte payload delivery ([entry point](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/EntryPoint.kt#L12-L27), [registration](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightSdkApplication.kt#L46-L79), [delivery](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightPushService.kt#L22-L60), [documented entry point](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/README.md#L356-L372), [TODO section](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/README.md#L431-L433)). | Real capability, but not a quick wrapper: Ink would need application-owned lifetime, unsolicited native events, endpoint hand-off to an application server, and a defined background execution policy. Defer until a push-backed app requires it. |
| Permission helpers | The audio guide says to request microphone permission but never shows the mechanism. Public source provides `checkPermission`, `rememberPermissionRequestLauncher`, and `PermissionRequestLauncher.launch`; the QR wrapper composes those helpers into the LightOS-owned permission flow ([permission API](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightServiceConnection.kt#L185-L224), [QR composition](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightClientUiUtils.kt#L33-L58), [incomplete audio instructions](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/README.md#L219-L246)). | Ink already follows the right architecture: typed permission reads plus a LightOS activity hand-off. Extend that one adapter for microphone and precise/approximate location rather than creating module-specific permission protocols. |
| LightOS user preferences | Public helpers read the user's haptics preference and keyboard configuration, including emoji set, voice-key visibility, key animation and swipe input. None is described in the docs ([haptics helpers](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightHapticsManager.kt#L19-L48), [keyboard helpers](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightKeyboardManager.kt#L23-L68), [response model](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/shared/src/main/kotlin/com/thelightphone/sdk/shared/LightServiceMethod.kt#L65-L90)). | These are host concerns, not application-facing Ink APIs. Keep haptic preference synchronisation in the Android adapter; consider applying the keyboard settings to Ink's keyboard without exposing raw LightOS preference objects. |
| Shared files and ringtone installation | The README only says that `fileShare` makes files readable by LightOS, although `LightFileShare` has read, write, list, existence, delete and content-URI operations. Combined with the documented-but-bare `SetRingtone` service method, it is a complete app-to-LightOS file hand-off path ([brief documentation](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/README.md#L66-L73), [file API](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightFileShare.kt#L11-L54), [ringtone request](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/shared/src/main/kotlin/com/thelightphone/sdk/shared/LightServiceMethod.kt#L56-L63)). | Worth adding only with a concrete export/install use case. Ink should expose an outcome-oriented action such as installing a generated ringtone, not the provider URI or shared-directory mechanics. |
| QR scanning | The docs mention `LightQrCodeScanner` only as a comparison for the NFC prompt. Source contains a full-screen, lifecycle-aware scanner and a client wrapper that checks and requests camera permission ([passing mention](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/README.md#L320-L329), [client wrapper](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightClientUiUtils.kt#L33-L58), [scanner contract](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/ui/src/main/kotlin/com/thelightphone/sdk/ui/LightQrCodeScanner.kt#L49-L66)). | The capability is useful, but Ink should implement a typed scan controller and its own visual treatment rather than importing the Compose screen. There is no general camera-capture SDK API here. |
| Host behaviour switches | `LightEntryPoint.enableRecentsScreenshots` controls whether Android may show a cached task screenshot. `LightActivity` also lets screens consume hardware key events, then forwards recognised unconsumed device keys to LightOS. Neither behaviour is covered by the client guide ([entry-point flag](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/EntryPoint.kt#L20-L27), [activity behaviour](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightActivity.kt#L90-L103), [key fallback](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightActivity.kt#L149-L215)). | Audit Ink's host for parity. These should remain internal activity policy unless an application demonstrates a reason to override them. |

## Metadata and permission gaps

`serverPackage` is required by the metadata parser and becomes the package used for the LightOS service binding, but the metadata documentation's schema and field list omit it. The checked-in tool file shows `com.lightos` for hardware and `com.thelightphone.sdk.emulator` for the emulator ([incomplete schema](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/docs/tool_metadata/README.md#L8-L56), [required parser field](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/plugin/src/main/kotlin/com/thelightphone/plugin/LightToolMetadata.kt#L56-L65), [sample values](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/tool/lighttool.toml#L1-L10)). Ink already owns the equivalent selection in its build configuration; it should continue to do so.

The metadata guide promises an allowlist “below” but does not enumerate it. Source currently accepts internet, network state, wake lock, vibration, notifications, camera, microphone, audio-library read, fine/coarse location and NFC permissions ([documentation](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/docs/tool_metadata/README.md#L38-L60), [allowlist](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/plugin/src/main/kotlin/com/thelightphone/plugin/LightToolMetadata.kt#L176-L188)). This is build policy, not an API catalogue:

- fine/coarse location, media-library read, notification posting and wake locks have no dedicated client API in this source;
- internet is ordinary networking, while the SDK's callable network surface is only connection-state observation;
- camera has a QR scanner, not a general camera API;
- the client manifest's optional USB-host feature is not a USB API ([manifest](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/AndroidManifest.xml#L1-L16)).

Likewise, `detached-audio` is a genuine capability because it generates permissions, a service and a marker consumed by the public audio player; it is not just allowlisting ([capability policy](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/plugin/src/main/kotlin/com/thelightphone/plugin/LightToolMetadata.kt#L190-L213), [generated service](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/plugin/src/main/kotlin/com/thelightphone/plugin/ManifestGenerator.kt#L41-L63)). NFC, audio, connectivity and background work are already substantially documented and are not hidden findings.

## Do not expose as application APIs

`GetToken`, `RequestPermissionComponent` and `DeviceKeyEvent` appear in the public shared method model, but source usage identifies them as authentication, permission-activity and activity-to-server plumbing. Ink should keep those inside its adapter. `LightSdkServer.customServiceMethodResolver`, certificate checks and permission-grant hooks are extension points for the application embedding the server in LightOS or the emulator, not capabilities available to a tool ([method model](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/shared/src/main/kotlin/com/thelightphone/sdk/shared/LightServiceMethod.kt#L35-L147), [server hooks](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/server/src/main/kotlin/com/thelightphone/sdk/server/LightSdkServer.kt#L127-L200)).

The UI module also contains many undocumented Compose components, while `SealedLightContext.readAsset` and `buildDatabase` are undocumented convenience functions. They are intentionally outside this recommendation: Ink owns its UI, asset loading and persistence, and none is a LightOS integration ([context helpers](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightActivity.kt#L229-L240), [Room helper](https://github.com/lightphone/light-sdk/blob/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/client/src/main/kotlin/com/thelightphone/sdk/LightDb.kt#L1-L8), [UI source](https://github.com/lightphone/light-sdk/tree/3df3c24a21247e70ad59e1bc0393ac6d63840bc2/sdk/ui/src/main/kotlin/com/thelightphone/sdk/ui)).

The best next Ink-facing addition is therefore the dialler action. Push is the largest genuinely missing capability; shared-file hand-off and QR scanning are useful later. Preference synchronisation, recents screenshots, key forwarding and protocol methods belong in the host adapter rather than Ink application code.
